# rd-20090515 source audit

**Audit date:** 2026-10-09  
**Scope:** LuckeeMiner native C++/Citro3D implementation, build configuration and release documentation, compared against the supplied extracted rd-20090515 Java source archive.

## Result

The source review found and addressed two concrete stability risks and one incorrect documentation claim. This is a source-audit result, **not** a claim that the release is fully verified on hardware.

## Findings fixed

1. **World-save stack pressure.** `Level::save()` had a 32 KiB automatic output buffer active while zlib was compressing. It is now static storage, removing that buffer from the small 3DS main stack. This was committed separately in [3cb204e](https://github.com/Dibbypeo/LuckeeMiner/commit/3cb204e3a63abfa44c242a2554e97fd2f452146f). The maintainer then confirmed SELECT-save and START-exit no longer produced crash dumps.
2. **Unbounded runtime entities/effects.** Pressing Y could grow the zombie vector and its character buffer without a limit; repeated block destruction could grow the particle list, per-particle collision storage, particle vertices, and linear VBO indefinitely. The native build now limits active zombies to 32 and particles to 512. Each particle reserves a smaller initial collision-query buffer, which can still grow automatically if needed. A destruction effect is admitted as a complete 64-particle burst or skipped when the pool cannot fit it. These are explicit original-3DS memory-safety budgets; normal behavior below the limits is unchanged.
3. **Incorrect compressed-byte claim.** The version notes claimed the native compressed GZIP bytes could be identical to Java's for matching DEFLATE implementations. The native writer explicitly uses `Z_BEST_SPEED`, while Java uses the default compression level, so that claim was too strong. Documentation now correctly describes GZIP and raw block-payload/layout compatibility, without promising byte-for-byte compressed identity.

## Source areas reviewed

Native project files include the application lifecycle/input loop, Level generation and GZIP I/O, tile registry and ticks, entity/AABB collision, player and zombie physics, particle lifetime/ownership, Java-compatible random arithmetic, Perlin terrain generation, texture decode/swizzle, frustum calculations, chunk mesh caching, terrain/character/particle rendering, picking/HUD state, shader source, Makefile, and control/version documentation.

The reference audit covered all 28 Java source files extracted from the supplied rd-20090515 archive:

- `RubyDung`, `Entity`, `Player`, `Timer`, `HitResult`, `Textures`, `MinecraftApplet`
- `Level`, `LevelListener`, `LevelRenderer`, `Chunk`, `DirtyChunkSorter`, `Frustum`, `PerlinNoiseFilter`, `Tesselator`
- `Tile`, `GrassTile`, `DirtTile`, `Bush`
- `Zombie`, `ZombieModel`, `Cube`, `Polygon`, `Vec3`, `Vertex`
- `Particle`, `ParticleEngine`, `AABB`

The reference contains desktop LWJGL/OpenGL code; those components are compared as behavior, with Citro3D/libctru used for the native implementation. The project intentionally does not copy Java source into the repository.

## Remaining release blockers

The following cannot be honestly marked complete by a source-only audit:

- Build the final `.3dsx` with the intended devkitPro toolchain.
- Verify world creation, save, close, relaunch and load on the target 3DS/2DS.
- Verify PC → 3DS → PC `level.dat` round-trip compatibility.
- Test terrain, lighting, block placement/breaking, D-Pad selection, zombie spawning/limit, grass/bush ticks, particles/limit, and normal exit on hardware.
- Confirm performance and stability over an extended play session.

No tag or public release should be described as fully verified until those release blockers pass.
